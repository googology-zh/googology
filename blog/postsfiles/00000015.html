C++ 模板元编程（二）：参数包、类型列表与竞赛中的用法

2026-11-21 · 编号 00000015

上一篇把"常量进入类型系统"与 SFINAE 讲完了。这一篇处理可变参数：包怎么展开、类型列表怎么增删查、index_sequence 怎么把包变成下标序列，最后讨论这些手段在竞赛代码里哪些值得用、哪些纯属给自己找麻烦。

一、参数包与展开位置

sizeof...(Ts) 给出包里元素的个数，它是编译期常量，可以直接用在数组维度与 static_assert 里。包的展开只允许出现在少数位置：函数调用的实参列表、模板实参列表、基类列表、花括号初始化列表、using 声明，以及 C++17 的折叠表达式。

经典的做法是递归剥离第一个参数，直到包为空：

template <class T>
void print(const T &x) { std::cout << x; }

template <class T, class... Rest>
void print(const T &x, const Rest &...rest) {
    std::cout << x << ' ';
    print(rest...);
}

这里的 rest... 在实参位置展开，每次递归减少一个参数，终止由单参数重载接管。若包里可能为空，还要一个零参数重载兜底，否则 print() 找不到匹配。

C++17 之后同类需求可以直接用折叠表达式：

template <class... Ts>
constexpr auto sum_all(Ts... xs) { return (xs + ... + 0); }

template <class... Ts>
constexpr std::size_t count_args(Ts &&...) { return sizeof...(Ts); }

(xs + ... + 0) 是二元右折叠，展开成 xs1 + (xs2 + (... + 0))，末尾的 0 让空包也有合法结果。少了它，包为空时表达式非法。同理，用 || ... 判断"任一类型满足条件"时也必须给初值 false，否则空包直接编译失败。

二、类型列表

把一组类型装进一个类模板，就有了可以在编译期增删查询的列表：

template <class... Ts> struct TypeList { static constexpr int size = sizeof...(Ts); };

template <class L> struct ListSize;
template <class... Ts>
struct ListSize<TypeList<Ts...>> : std::integral_constant<int, sizeof...(Ts)> {};

template <class L, class T> struct PushFront;
template <class... Ts, class T>
struct PushFront<TypeList<Ts...>, T> { using type = TypeList<T, Ts...>; };

template <int I, class L> struct Nth;
template <class T, class... Ts>
struct Nth<0, TypeList<T, Ts...>> { using type = T; };
template <int I, class T, class... Ts>
struct Nth<I, TypeList<T, Ts...>> : Nth<I - 1, TypeList<Ts...>> {};

template <class T, class L> struct Contains;
template <class T, class... Ts>
struct Contains<T, TypeList<Ts...>>
    : std::bool_constant<(std::is_same_v<T, Ts> || ...)> {};

几个要点。PushFront 的偏特化把 TypeList<Ts...> 拆开，再拼上 T；Nth 用 I - 1 递归剥离头部，I = 0 时由偏特化取出首元素。Contains 借助折叠表达式一次性比较所有元素，但它在空列表上非法——需要空包特化返回 false_type。

写成这个形状之后，static_assert 就能把每条性质固定下来：

using L0 = TypeList<int, double, char>;
static_assert(ListSize<L0>::value == 3);
static_assert(std::is_same_v<PushFront<L0, long>::type, TypeList<long, int, double, char>>);
static_assert(std::is_same_v<Nth<1, L0>::type, double>);
static_assert(Contains<double, L0>::value);
static_assert(!Contains<float, L0>::value);

类型列表的实际价值在于"按类型索引"。运行期的多态要虚函数或函数指针，编译期的分派可以直接由类型在列表中的位置决定。标准库的 std::variant 与 std::visit 就是这套思路的成品，自己搭一套通常只为了少一次间接调用。

三、index_sequence 展开

有些操作需要的不是类型本身，而是下标：遍历 tuple、批量构造数组、把包映射到另一个包。std::make_index_sequence<N> 生成 0..N-1 的编译期序列，配合逗号折叠就能按顺序展开：

template <class F, class T, std::size_t... I>
void for_each_impl(F &&f, T &&t, std::index_sequence<I...>) {
    (f(std::get<I>(t)), ...);
}

template <class F, class T>
void for_each_tuple(F &&f, T &&t) {
    constexpr std::size_t n = std::tuple_size_v<std::remove_reference_t<T>>;
    for_each_impl(std::forward<F>(f), std::forward<T>(t), std::make_index_sequence<n>{});

(f(std::get<I>(t)), ...) 是逗号折叠，按 I 递增的顺序逐个求值。逗号运算符保证从左到右，这一点与函数实参的求值顺序不同——后者在 C++17 之前是未指定的，不要指望用实参展开来做有顺序依赖的事。

tuple_size_v 要求类型不是引用，所以先 remove_reference_t；n 声明为 constexpr 才能当模板实参。这两处是这类代码最常见的编译错误来源。

四、竞赛里到底用不用

结论先说：绝大多数题不需要 TMP。DP、图论、数据结构的常数瓶颈在访存与分支，不在类型分派。真正值得用的场合有三类。

第一类是把模数做成模板参数。模数成为编译期常量后，编译器可以把取模换成常量除法优化，且不同模数的实例互不干扰：

template <int MOD>
struct ModInt {
    int v;
    static constexpr int mod = MOD;
    constexpr ModInt(long long x = 0) : v(int((x % MOD + MOD) % MOD)) {}
    constexpr ModInt operator+(ModInt o) const { return ModInt(v + o.v); }
    constexpr ModInt operator*(ModInt o) const { return ModInt(1LL * v * o.v); }
    constexpr ModInt pow(long long e) const {
        ModInt r(1), a(*this);
        while (e) { if (e & 1) r = r * a; a = a * a; e >>= 1; }
        return r;
    }
};

第二类是消除运行期分派。线段树的合并、并查集的合并若写成 std::function，每次调用都是一次间接跳转；改成模板参数传入函数对象，调用点可内联，常数差一个数量级。

第三类是用 static_assert 把前提写死。例如预处理了一张质数表，可以断言表长与上界的关系；模板参数写错时在编译期就停下，而不是在评测机上跑到一半越界。

不值得用的场合同样清楚：为了"优雅"把简单循环写成类型递归，为了少写几个函数而堆 enable_if，以及在需要快速改代码的比赛环境里引入只有自己能看懂的模板层。编译错误一旦出现，模板栈的阅读成本远高于多写两行普通代码。

五、易错点

  • 空包上的折叠表达式没有初值，(xs + ...)、(cond || ...) 都会直接失败。
  • 递归剥离参数包时忘了零参数终止重载，包为空的那一次调用无匹配。
  • sizeof...(Ts) 与 sizeof(Ts)... 是两回事，后者展开成每个类型的大小，语义完全不同。
  • 模板定义分散在多个翻译单元时，各处定义必须一致，否则违反 ODR，链接期报重复符号或行为不定。头文件里定义、源文件里只做实例化是常规做法。
  • 递归深度受限，线性递归在元素多时撞上限；能二分就二分，能 constexpr 循环就循环。

验证方式很直接：所有编译期结论都写成 static_assert，编译通过即证明；运行期行为再用普通断言比对。本文两篇里的代码都在 GCC 16 上以 -std=c++17 -Wall -Wextra 编译过，没有警告。
